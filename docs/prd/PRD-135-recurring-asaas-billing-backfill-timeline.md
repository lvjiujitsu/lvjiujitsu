# PRD-135: Automated recurring Asaas billing synchronized with family discounts and historical timeline-event backfill

## Summary
This PRD addresses two items explicitly left **out of scope** in PRD-134 and requested by the user as a separate PRD. (A) There is currently no recurring billing automation for Asaas memberships: each charge is an individual payment, and whenever a new charge is generated, its amount is recalculated from the full catalog price, **ignoring** `Membership.billed_price` (the already-correct amount with the family discount applied). (B) The PRD-134 timeline records only new events after deployment. This PRD retroactively populates events that already have a trace in existing fields (`Membership.canceled_at`, `RegistrationOrder.paid_at`/`refunded_at`, and `MembershipPauseRequest.created_at`/`decided_at`).

## Demand type
Architectural gap correction (A) and data task (B), both explicitly requested by the user.

## Current problem

### Part A — recurring Asaas billing
- `system/services/asaas_client.py` exposes only `create_pix_payment`/`create_credit_card_payment`, which create individual payments (`POST /payments`). This project has no Asaas-side "subscription" concept.
- No management command, cron, Celery worker, or scheduled task generates the next charge when `Membership.current_period_end` expires. An exhaustive search during this session confirmed there is no billing/renewal command in `system/management/commands/` and no Celery/APScheduler/django-cron dependency in the project.
- When an Asaas renewal charge is created manually today, the amount always comes from `plan.price`/`plan_price_ref.price`, the full catalog price (`system/services/registration_checkout.py`, `_create_paid_plan_order` in `system/services/dependent_registration.py`), and **never** from `Membership.billed_price`, which already reflects the current family discount.
- The same session confirmed that payment confirmation **already works correctly** when a new renewal `RegistrationOrder` is paid: `_handle_payment_event` (`system/services/asaas_webhooks.py:135-176`) calls `activate_membership_from_paid_order` (`system/services/membership.py:154-199`), which finds the existing active `Membership` (by `person` plus `plan`/`plan_price`, excluding cancelled/expired records) and extends `current_period_start`/`current_period_end` with `add_billing_cycle`. **The gap is not confirmation. It is that nothing automatically creates the renewal charge, and the amount used when someone creates it manually is incorrect.**
- Practical result: an eventual renewal for an Asaas client with a family discount, if and when manually generated by an admin, would charge the full price rather than the discounted amount. This is the inverse of what PRD-134 investigated: it is not "the discount remained incorrectly applied"; it is "the only way to charge again ignores the discount that should apply."

### Part B — historical event backfill
- PRD-134 creates `MembershipTimelineEvent`, but intentionally performs **no** backfill; the timeline begins only when that PRD is deployed.
- Partial historical data already exists and can create retrospective events without inventing information: `Membership.canceled_at` (cancellation), `Membership.created_at` (creation/enrollment), `RegistrationOrder.paid_at` (confirmed payment), `RegistrationOrder.refunded_at` (refund), `MembershipPauseRequest.created_at` (pause requested), and `MembershipPauseRequest.decided_at` with `status` (pause approved/rejected).
- Events without an isolated historical field (for example, dependent addition/removal, plan changes, or card changes before this PRD) **cannot be reconstructed accurately**. There is no equivalent field such as "date the dependent was removed" outside unstructured logs. Those events are excluded from the backfill and documented as a limitation.

## Goal
1. Every active Asaas `Membership` (`asaas_pix`/`asaas_card`) automatically generates the next cycle's charge before its due date, using the correct amount (`billed_price`, which already reflects the family discount), without manual intervention.
2. Confirmation of that automatically generated charge extends the validity period exactly as it does today for manually created orders. The already-correct confirmation path does not change.
3. `MembershipTimelineEvent` (PRD-134) is retroactively populated with events that have a reliable trace in an existing field, without inventing data for events that do not.

## Scope

### Part A — recurring Asaas billing
1. New `system/services/asaas_billing_cycle.py`: `find_due_asaas_memberships(lead_days=N)` finds memberships whose `effective_gateway_code` is `asaas_pix` or `asaas_card`, whose status is `ACTIVE`, that have no active approved pause, whose `current_period_end` falls within the lead window, and that have no pending/paid `RegistrationOrder` already covering the next cycle.
2. `generate_due_asaas_charge(membership)` creates a `RegistrationOrder` with `total = membership.billed_price if membership.family_discount_applied else membership.effective_full_price`, calls `create_pix_payment`/`create_credit_card_payment` according to `effective_payment_method`, and saves `asaas_payment_id`.
3. New `system/management/commands/generate_due_asaas_charges.py` invokes `find_due_asaas_memberships` plus `generate_due_asaas_charge` for each membership and logs what was generated or skipped.
4. No change to the confirmation path (`_handle_payment_event`/`activate_membership_from_paid_order`), which already works correctly.
5. Document the Render Cron Job configuration for HG/production in this PRD, not in code. It is outside the repository and is an infrastructure decision to confirm with the user before deployment. Suggested frequency: daily.

### Part B — timeline backfill
1. New `system/management/commands/backfill_membership_timeline.py`, dependent on the PRD-134 `MembershipTimelineEvent` model. For each existing `Membership`/`RegistrationOrder`/`MembershipPauseRequest`, create the corresponding `MembershipTimelineEvent` when the source field exists and no event has already been created for that combination (idempotency through a duplicate check before creation).
2. Mapping: `Membership.canceled_at` → `MEMBERSHIP_CANCELED` (`actor=None`, `context={"backfilled": true}`); `RegistrationOrder.paid_at` → `PAYMENT_CONFIRMED`; `RegistrationOrder.refunded_at` → `REFUND_ISSUED`; `MembershipPauseRequest.created_at` → `PAUSE_REQUESTED`; `MembershipPauseRequest.decided_at` when `status` is approved/rejected → `PAUSE_APPROVED`/`PAUSE_REJECTED`.
3. Mark backfilled events with `context={"backfilled": true, ...}` to distinguish them from real-time captured events for audit/debugging without changing the client presentation.

## Risks and edge cases
- A duplicate charge if the command runs twice on the same day before confirmation of the first payment. Mitigate by checking for an existing pending `RegistrationOrder` before creating another.
- A membership's family discount can change between charge generation and payment (for example, if a dependent is removed in the meantime). The generated charge retains the amount frozen at creation, as any already-issued charge does; the next cycle reflects the updated amount.
- Production backfill with a large historical volume of `Membership`/`RegistrationOrder` records. Mitigate with batching/pagination in the command.
- `context={"backfilled": true}` could leak confusingly into the client timeline. `describe_for_client`/`describe_for_admin` from PRD-134 must not expose this marker to the client and may use it only internally for admin purposes.

## Rules and constraints
- No new migration in this PRD. Part A does not change the schema, and Part B only populates an existing PRD-134 model.
- No real gateway calls in automated tests; mock `create_pix_payment`/`create_credit_card_payment`.
- Both management commands must be idempotent.
- Use `transaction.atomic` for each charge generation and each event backfill.

## Implemented
- Part A: `system/services/asaas_billing_cycle.py` (`find_due_asaas_memberships`, `generate_due_asaas_charge`, `generate_due_asaas_charges`) reuses the existing `create_pix_charge_for_order`/`create_credit_card_charge_for_order` from `asaas_checkout.py`. Idempotency uses `context__source_id`, a stable key for each source record such as `membership_canceled:<pk>`. It bypasses `auto_now_add` through `.update()` to preserve the actual historical date. Management command: `backfill_membership_timeline`.
